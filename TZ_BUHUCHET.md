# ТЗ и дорожная карта: переход «Зарплата ТМ» к полному бухучёту (двойная запись)

Этот документ дополняет `TZ.md` (исходное ТЗ на модуль расчёта зарплаты) и
описывает следующий этап жизни проекта — вырастить его до полноценной
бухгалтерской программы с двойной записью для Туркменистана, с одновременной
работой нескольких пользователей по сети.

Ведётся и обновляется в ветке `accounting-edition`. Ветка `main` /
`claude/reports-browser-all-os-v8m0et` остаётся отдельным, более простым
продуктом («только зарплата») для тех, кому полный бухучёт не нужен.

## 1. Цель

Превратить текущее приложение (кадры + расчёт зарплаты, локальная SQLite,
один пользователь) в многопользовательскую бухгалтерскую систему с
двойной записью, покрывающую:

- план счетов и журнал проводок (Главная книга);
- автоматическую разноску зарплаты по счетам;
- кассу и банк;
- расчёты с контрагентами (дебиторы/кредиторы);
- регламентированную отчётность (баланс, ОФР, налоговые формы) —
  по формам и плану счетов Туркменистана.

## 2. Принцип: эволюция, а не переписывание с нуля

Технически обоснованное решение (см. обсуждение в самом начале этой работы):
Delphi/VCL и FireDAC остаются — это не узкое место. Меняются/добавляются:

1. **База данных**: SQLite → PostgreSQL (для одновременной работы
   нескольких пользователей по сети). Драйвер `FireDACPgDriver` уже
   подключён в `Salary.dproj` — использовать его.
2. **Новый слой данных**: план счетов + проводки + Главная книга —
   отдельное ядро, ничего общего по структуре с текущими
   `employees`/`payroll_journal`.
3. **Существующие модули не переписываются**, а дополняются: расчёт
   зарплаты, отпускных, больничных начинает формировать проводки в новое
   ядро, помимо того, что уже умеет (расчёт, печать ведомостей).

## 3. Целевая архитектура (итоговая картина)

```
Delphi/VCL клиент (как сейчас) ──► PostgreSQL (было: SQLite)
   │
   ├─ Кадры / Зарплата / Отпуска / Больничные (как сейчас)
   │      │
   │      └─ формируют проводки ──┐
   │                               ▼
   ├─ Касса / Банк (новое)  ──►  ЯДРО: План счетов + Журнал проводок
   │                               │         + Главная книга
   ├─ Контрагенты (новое)  ──►────┘
   │
   └─ Регламентированная отчётность (новое): баланс, ОФР, ОСВ,
      налоговые формы — читают данные из ядра
```

Роли пользователей (кассир/бухгалтер/директор) и аудит (кто/когда/что
изменил) — сквозные требования для всех новых модулей.

## 4. Что нужно от вас по ходу дела

Это не разовая передача, а по этапам — каждый пункт нужен ровно к тому
этапу, где он используется, не раньше:

- **План счетов Туркменистана** (код, название, тип счёта — актив/пассив,
  вложенность/субсчета) — нужен на Этапе 2.
- **Формы обязательной отчётности** (баланс, отчёт о финрезультатах,
  налоговые декларации — точные графы) — нужны на Этапе 6.
- **Примеры "эталонных" проводок** для 2-3 реальных операций (например,
  как именно должна разноситься начисленная зарплата по счетам) — очень
  желательно на Этапе 3, чтобы проверить мост «Зарплата → проводки»
  на реальном примере, а не по абстрактной схеме.
- **Доступ к серверу PostgreSQL** (у вас он уже есть через OpenServer) —
  нужен на Этапе 1: хост/порт/логин для тестового подключения.

## 5. Этапы

### Этап 0 — Уже сделано ✅
- Отчёты переведены на `TWebBrowser` (работают на Win 7/8/10/11 без
  установки WebView2).
- Репозиторий очищен от мёртвого кода, IDE-кэшей, бинарника БД в git,
  дублирующихся SQL-файлов.
- Создана отдельная ветка `accounting-edition`.

### Этап 1 — База данных и многопользовательский доступ
**Цель:** несколько человек работают одновременно, не разрушая друг другу
данные.

- Перевод `UnitdmMain` (`TFDConnection`) с SQLite на PostgreSQL.
- Перенос существующей схемы (`employees`, `departments`,
  `payroll_journal`, `settings` и т.д. — из `database/sql/`) на
  PostgreSQL-диалект.
- Экран/файл настройки подключения (хост, порт, БД, логин) — раньше это
  был просто путь к файлу рядом с exe, теперь нужен сетевой адрес.
- Роли пользователей (расширить `UnitLogin`): администратор / бухгалтер /
  кассир — как минимум различие прав на чтение/запись по модулям.
- Таблица аудита (кто/когда/что изменил) — фундамент, на который потом
  опираются проводки (документы в бухучёте нельзя тихо менять/удалять).

**Критерий готовности:** два человека на разных компьютерах одновременно
открывают программу, видят одни и те же данные, изменения одного видны
другому после обновления.

### Этап 2 — Ядро двойной записи
**Цель:** появляется настоящий бухучёт — план счетов и проводки.

- ✅ Таблица `accounts` (план счетов) — заполнена из присланного плана
  счетов (441 счёт). Без жёсткого дерева «счёт → субсчета»: в самих
  данных родительские коды групп по большей части не существуют как
  отдельные строки (проверено — 280 из 429 «листовых» счетов), поэтому
  для группировки хватает текстовых полей `category`/`subcategory`/
  `acct_group`, без строгой иерархии (это же соответствует просьбе не
  жёстко проверять план счетов — это просто справочник).
- ✅ Таблица `journal_entries` (документ-проводка): дата, номер,
  описание, автор, статус (черновик/проведён) — `database/postgres/007_ledger_core.sql`.
- ✅ Таблица `journal_lines` — классическая форма проводки как в 1С:
  одна строка = счёт дебета + счёт кредита + сумма (не отдельная
  колонка дебет/кредит на каждый счёт). У такой формы сумма дебета и
  кредита совпадают по конструкции самой строки — отдельная проверка
  «дебет = кредит по документу» не нужна.
- ⏳ Правило «проведённый документ не редактируется и не удаляется —
  только сторно (обратная проводка)» — на уровне БД статус `posted`
  уже есть, сама блокировка правки/удаления и кнопка «Сторно» — в
  Delphi-форме ввода проводок (следующий шаг, ещё не сделано).
- ⏳ Экран ручного ввода проводки + Главная книга (движения по счёту) +
  оборотно-сальдовая ведомость (ОСВ) — ещё не сделано.

**Нужно от вас:** план счетов — получен, схема заполнена. `account_type`
в нём остаётся черновой разметкой (см. `database/coa/README.md`) —
можно уточнить у бухгалтера позже, на работу проводок сейчас это не
влияет.

**Критерий готовности:** можно вручную ввести проводку, увидеть её в
Главной книге по обоим счетам, увидеть остатки в ОСВ.

### Этап 3 — Мост «Зарплата → проводки»
**Цель:** существующий расчёт зарплаты автоматически формирует проводки,
а не только печатает ведомости.

- При проведении начисления зарплаты — автоматическое создание
  `journal_entries`/`journal_lines` (начисление ФОТ, налоги, взносы —
  по счетам, которые вы укажете на реальном примере).
- То же для отпускных и больничных.
- Отчёты (расчётный листок, ведомость) остаются как есть — просто рядом
  появляется факт разноски по счетам.

**Нужно от вас:** эталонные проводки (см. раздел 4).

**Критерий готовности:** после начисления зарплаты за период в Главной
книге видны все ожидаемые движения по счетам ФОТ/налогов/взносов.

### Этап 4 — Касса и банк
- Приходные/расходные кассовые ордера.
- Банковские платежи/поступления (ручной ввод, без интеграции с
  банк-клиентом — это отдельная большая тема при необходимости).
- Оба модуля формируют проводки в общее ядро, как и зарплата.

### Этап 5 — Контрагенты (дебиторы/кредиторы)
- Справочник контрагентов.
- Простые расчётные документы (счета/акты), взаиморасчёты, сальдо по
  контрагенту.

### Этап 6 — Регламентированная отчётность
- Баланс, отчёт о финансовых результатах — по формам, которые вы
  предоставите.
- Закрытие периода (запрет правок задним числом после закрытия).

**Нужно от вас:** формы отчётности (см. раздел 4).

### Этап 7 — Права доступа и аудит (углубление)
- Детальные права по ролям (кто что видит/правит).
- Полноценный журнал аудита с UI-просмотром истории изменений.

### Этап 8 — По потребности (не обязательно)
Основные средства и амортизация, склад/себестоимость, мультивалютность —
добавляем только если реально нужно, не заранее.

## 6. Как будем работать

- Идём по этапам последовательно, каждый — отдельными коммитами/пушами
  в `accounting-edition`, с понятным критерием готовности.
- Каждый этап собирается и (по возможности) проверяется вами в реальной
  Delphi — как и с отчётами, я не могу скомпилировать/запустить проект
  сам (у меня нет Windows/Delphi), поэтому обратная связь по компиляции
  и по факту важна на каждом шаге.
- То, что нужно от вас (план счетов, формы, эталонные проводки) — прошу
  по мере приближения к соответствующему этапу, не всё сразу.

## 7. Открытые вопросы / риски

- Точный план счетов и формы отчётности Туркменистана — не берусь
  придумывать сам, только по вашим материалам (см. раздел 4).
- Не решено: нужна ли интеграция с банк-клиентом/фискальными органами
  (обычно самая трудоёмкая и юридически значимая часть) — обсудим
  отдельно, когда дойдём до Этапа 4-6.
- Не решено: нужна ли сертификация/регистрация ПО как бухгалтерского
  софта по законодательству Туркменистана — это не техническая
  задача, но может повлиять на объём работы; уточните при возможности.
