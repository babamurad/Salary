# PostgreSQL — создание базы (Этап 1)

## Как применить

```
psql -U <ваш_пользователь> -d <имя_базы> -f 001_initial_schema.sql
psql -U <ваш_пользователь> -d <имя_базы> -f 002_users_roles.sql
```

(или через pgAdmin / DBeaver — просто выполнить оба файла по очереди в Query
Tool на нужной базе; сначала `001`, потом `002`).

Саму базу данных (`CREATE DATABASE ...`) нужно создать заранее — эти
скрипты создают только таблицы внутри неё.

**Если база уже была создана раньше** (`001`/`002` уже выполнялись до
исправления TEXT → VARCHAR, см. `003` ниже) — примените ещё и:

```
psql -U <ваш_пользователь> -d <имя_базы> -f 003_fix_text_columns.sql
```

Иначе будет падать `EDatabaseError: Type mismatch ... expecting:
WideString actual: WideMemo` при открытии почти любого запроса со
строковыми полями. На новых базах, где `001`/`002` выполняются впервые
(уже с VARCHAR), файл `003` не нужен.

Также если база была создана до исправления денежных полей (`001` со
старым `NUMERIC(18,2)` вместо `MONEY` для `base_salary` и полей
`payroll_journal`) — примените и:

```
psql -U <ваш_пользователь> -d <имя_базы> -f 004_fix_currency_columns.sql
```

Иначе часть запросов падает с `Type mismatch ... expecting: Currency
actual: FMTBcd` (или наоборот, `expecting: FMTBcd actual: Currency`,
если чинить это одним общим правилом на всё подключение — оба типа
несовместимы в рамках одной группы полей, нужно разделять именно на
уровне типа колонки).

Также если база была создана до исправления `sick_leave_rates` (`001`
со старым `INTEGER` вместо `BIGINT` для `max_years`) — примените по
порядку оба:

```
psql -U <ваш_пользователь> -d <имя_базы> -f 005_fix_sick_leave_rates_bigint.sql
psql -U <ваш_пользователь> -d <имя_базы> -f 006_fix_sick_leave_rates_min_years.sql
```

(`005` переводит обе колонки в `BIGINT`; это оказалось неверно для
`min_years` — там всегда небольшое число, и `006` возвращает её обратно
в `INTEGER`, оставляя `max_years` в `BIGINT`). Без `005` падает
`qrySickLeaveRates` с `Type mismatch ... expecting: LargeInt actual:
Integer` (на `max_years`); применив только `005` без `006` — тот же
запрос падает наоборот, `expecting: Integer actual: LargeInt` (на
`min_years`).

## Что внутри

- **`001_initial_schema.sql`** — точный перевод действующей схемы SQLite
  (`database/schema/salarydb_schema_only.sql`, реальный экспорт из рабочей
  `salarydb.db`) на PostgreSQL. Имена таблиц и колонок не менялись —
  весь код на Delphi, обращающийся к ним по имени, продолжит работать.
  Строковые колонки — `VARCHAR(N)` с запасом по длине, а не голый `TEXT`
  (у голого `TEXT` в Postgres нет объявленной длины, и FireDAC мапит его
  в `WideMemo`, а не в `WideString`, которую ждёт старый код). Денежные
  поля, которые в SQLite были типом `CURRENCY` (а не `DECIMAL`) —
  `MONEY`, а не `NUMERIC(18,2)` (см. `004` ниже, почему это важно).
- **`002_users_roles.sql`** — новые таблицы `app_users` (логин/пароль/роль)
  и `audit_log` (журнал аудита) для многопользовательской работы. Заведён
  пользователь по умолчанию `admin` / `admin` (пароль обязательно сменить
  после первого входа, когда появится экран смены пароля).
- **`003_fix_text_columns.sql`** — миграция для баз, созданных ДО этого
  исправления: переводит те же колонки из `TEXT` в `VARCHAR(N)` на уже
  существующей базе (`001`/`002` используют `CREATE TABLE IF NOT EXISTS`
  и повторный запуск их не обновит).
- **`004_fix_currency_columns.sql`** — миграция для баз, созданных ДО
  исправления денежных типов: переводит `base_salary` и денежные поля
  `payroll_journal` из `NUMERIC(18,2)` в `MONEY` на уже существующей базе.
- **`005_fix_sick_leave_rates_bigint.sql`** — миграция для баз, созданных
  ДО исправления `sick_leave_rates`: переводит `min_years`/`max_years`
  из `INTEGER` в `BIGINT` на уже существующей базе.
- **`006_fix_sick_leave_rates_min_years.sql`** — правка поверх `005`:
  возвращает `min_years` обратно в `INTEGER` (в `BIGINT` нужно было
  перевести только `max_years`).

## Про ошибки "Type mismatch" в целом

Все выше — один и тот же класс проблемы: в DFM-файлах форм есть
persistent-поля (созданные когда-то в дизайнере при подключении к
SQLite), которые жёстко запоминают тип поля на момент создания. SQLite
из-за динамической типизации (manifest typing) иногда даёт для одной и
той же объявленной колонки более широкий/другой тип, чем строгий
PostgreSQL. Проверить конкретное поле заранее (не дожидаясь падения
программы) можно в psql:

```sql
SELECT column_name, data_type FROM information_schema.columns
WHERE table_name = '<имя_таблицы>';
```

и сравнить со строкой в `database/schema/salarydb_schema_only.sql` для
той же колонки — если там `INTEGER PRIMARY KEY` (без AUTOINCREMENT) или
видно, что значения могут быть очень большими (условная
"бесконечность", коды-счётчики и т.п.) — велик шанс, что нужен `BIGINT`,
а не `INTEGER`, в Postgres.

## Этап 2 — ядро двойной записи

- **`007_ledger_core.sql`** — таблицы `accounts` (план счетов),
  `journal_entries` (документ-проводка: дата, номер, статус
  черновик/проведён) и `journal_lines` (сами проводки — классическая
  форма "счёт дебета + счёт кредита + сумма" в одной строке, как в 1С;
  документ обычно состоит из нескольких таких строк). Применять после
  `001`–`006`:

  ```
  psql -U <пользователь> -d <база> -f 007_ledger_core.sql
  ```

- **`008_seed_accounts.sql`** — заполняет `accounts` из
  `database/coa/turkmenistan_chart_of_accounts.csv` (441 счёт, лист
  "старый+новый"). Применять после `007`:

  ```
  psql -U <пользователь> -d <база> -f 008_seed_accounts.sql
  ```

  `account_type` в этих данных — черновая разметка (см.
  `database/coa/README.md`), программой никак не проверяется и ни на
  что не влияет — план счетов используется просто как справочник.

## Что дальше

Подключение к PostgreSQL уже реализовано в `UnitdmMain.pas`
(`Driver=PG` в `config.ini`, см. `Win32/Debug/config.ini.example`) —
работает параллельно со старым режимом SQLite. Использование `app_users`
для входа в программу подключим отдельным шагом (сейчас логин
по-прежнему проверяет общий пароль в `company_info`, как и раньше — это
единственное, что временно не тронуто в этом этапе).

Таблицы Этапа 2 (`accounts`/`journal_entries`/`journal_lines`) готовы,
но UI в Delphi (план счетов, ручной ввод проводки, Главная книга, ОСВ)
— следующий шаг.
